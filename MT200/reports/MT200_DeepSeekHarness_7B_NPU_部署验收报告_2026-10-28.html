1. 执行摘要

最终结论：链路已经跑通。用户从本机 127.0.0.1:3080 进入 DeepSeek Harness，SSH 隧道把请求送到 MT200；MT200 上的 dsh 通过 OpenAI 兼容桥调用 Qualcomm Genie，最终由 Hexagon V73 NPU 执行 7B W4A16 模型。两轮连续会话验收成功，服务均开机自启。

  • 关键修复：按 DeepSeek Harness 官方 minimal persona 机制设置 complete: true 与 includeRuntimeContext: false，把 Web 首轮提示从溢出的规模压到 1024-token bundle 可承载范围。
  • 没有伪装：这不是 FP16 权重模型。当前是 W4A16，即权重 INT4、激活 FP16；纯 FP16 7B/8B 权重分别约 14/16 GB，超过 MT200 物理内存。
  • 当前边界：现有 bundle 的 1024 token 是编译期硬上限，当前只能做短对话；工具 schema、长历史、文档分析和完整 Agent 暂不成立。

3. 成功部署参数

3.1 DeepSeek Harness provider 与最小 persona

# /home/ubuntu/.dsh/profiles/{web,headless}/cordis.patch.yml（关键项）
provider: meig-npu
model: deepseek-7b-npu
api: openai-completions
baseURL: http://127.0.0.1:8090/v1
contextWindow: 1024
maxTokens: 256
compat:
  supportsDeveloperRole: false
  maxTokensField: max_tokens
persona:
  prefix: You are a concise Chinese assistant. Answer directly and briefly.
  complete: true
  includeRuntimeContext: false

complete 让 persona 成为唯一系统提示段；includeRuntimeContext: false 关闭可选运行时上下文。两项必须同时使用，否则 Web bundle 仍会注入身份、开发环境说明、目录上下文和工具相关文本。

6. 两个关键故障及修复

6.1 pi-ai context overflow

阶段现象根因修复
初始接入pi-ai detected context overflow只删工具不够；Web 全局提示约 2752 字符、runtime context 约 716 字符，另有 working-directory schema。bridge 上报的 input usage 估算为 1764/1765，超过 1024。采用官方 minimal persona 机制：complete: true + includeRuntimeContext: false；新建会话。
修复后两轮短对话成功提示收敛到数百字符，bridge usage 估算低于窗口保留 chat-only；工具全部禁用

注意：bridge 当前用字符长度近似填充 OpenAI usage，这不是 DeepSeek tokenizer 的精确计数；但 bundle 的 1024 上限是真实硬约束。

6.2 SSE/finish_reason 兼容

原 bridge 无论客户端是否请求流式都返回普通 JSON，pi-ai 报 Stream ended without finish_reason。修复后，stream=true 返回 text/event-stream，先发送内容 chunk，再发送 finish_reason: stop，最后发送 [DONE]。当前 Genie 是一次性 CLI，所以这是“完成后一次性 SSE”，不是逐 token 流式。

7. 参数量提升与量化可能性

本节把用户提出的“提高参数和量化”理解为：在 MT200 上提高模型参数量，同时选择能放入内存并可由 QNN/Genie 执行的精度。

方案仅权重粗算上下文/固定开销后可行性
7B FP16约 14 GB大于 15 GB不可能：权重已超过 10.86 GiB
8B FP16约 16 GB大于 17 GB不可能
7B INT8 / W8A8约 7 GB加图缓冲、KV 和系统后接近或超过设备容量没有安全余量
8B INT8 / W8A8约 8 GB固定开销后明显超限不可用
当前 7B W4A16bundle 约 4.40 GBbridge cgroup 峰值约 5.52 GB已运行；但上下文仅 1024
8B W4A16 + GQA约 4.5 GB若固定开销 ≤1.5 GB：4K 约 6.5 GB，8K 约 7.0 GB需厂商重新制作 bundle
3B/4B W4A16 + 8K约 1.7–2.3 GB内存余量明显更大最稳妥的长上下文 NPU 备选
W3/W2更小依赖算子支持、校准数据和质量评估理论可行，当前无可用 bundle

7.1 8B + 长上下文成立的必要条件

  1. W4A16：权重必须保持 4 bit 级；FP16 只用于激活/计算。
  2. GQA 且 KV heads ≤ 8：把 KV cache 控制到约 128 KB/token；4K 约 0.5 GB，8K 约 1.0 GB。
  3. 词表 ≤ 32K，或共享/拆分 embedding 与输出层：当前 102.4K 词表会增加固定开销。
  4. 固定开销 ≤ 1.5 GB：需在图缓冲、激活和 HVX 工作区上优化；不能沿用约 3.3 GB 的旧开销。
  5. bundle 编译 context=4096/8192：运行时改 JSON 不能替代重新导出。
  6. batch=1：当前是单用户 Agent，不应为无用并发支付内存。

7.2 模型选择优先级

优先级模型方向理由
P07B/8B W4A16，8K context，GQA质量、Agent 提示容量和 NPU 速度最均衡
P13B/4B W4A16，8K context若 8B 内存优化失败，优先保住完整 Agent 上下文
P28B Q4 GGUF，CPU 离线批处理不依赖厂商 bundle，但交互慢且存在严重散热风险
不建议7B/8B FP16 权重；更大 dense 模型物理内存不成立

8. 当前瓶颈

瓶颈直接影响根本解法
1024-token 编译窗口只能短对话；完整工具 schema 和长历史无法进入模型重新导出 4K/8K QNN bundle
Genie 每请求新进程每轮支付约 7–10.5 s 初始化；没有真正流式首字常驻 Genie API，或修复可用的 save/restore
bridge 无 tool_calls当前必须关闭工具，不能形成完整 Agent 闭环增加函数调用模板、解析器和 OpenAI tool_calls/result 映射
pi-ai 面向大窗口设计其输出预算逻辑保留较大安全空间；1K 路由需要极简兼容配置优先换长上下文 bundle，不应虚报 contextWindow
内存无 swap模型、KV、dsh 和系统抢同一 10.86 GiB；失败时可能直接 OOM压固定开销；限定单并发；保留系统余量
散热CPU 8B 达 114.8°C；NPU 长请求也需风冷主动风冷 + 90°C 硬门禁 + 负载限时
模型不接地会编造时间、OS 和设备状态长上下文后恢复最小系统工具；当前由 bridge 注入少量可信元数据
峰值 TOPS 与 LLM 不等价单序列 decode 受访存、图和调度限制，远低于 200 TOPS 标称看 tok/s、TTFT、内存和温度，不用 TOPS 单点判断体验

9. 下一步设计

  1. 先保设备：新增独立温度守护；任一关键热区 ≥90°C 时拒绝新请求并停止推理，降至 75°C 后才允许恢复。
  2. 向厂商索取真正可验收的 bundle：7B/8B W4A16、GQA、8K context、batch 1、固定开销 ≤1.5 GB，并交付量化参数和性能 profile。
  3. 把 Genie 常驻：当前 CLI 每轮冷启动。应使用 Genie API 保留 dialog，或先验证可靠的 state restore，目标把短问答从约 17 s 降到 3–6 s。
  4. 恢复真实流式：当前桥接必须等待 Genie 退出才发送 SSE。改用 token callback 后，用户可在约 TTFT 时看到首字。
  5. 补最小工具闭环：优先只开放时间/系统信息与一个受限 shell 工具；但前提是 context ≥4K 且 bridge 支持 tool_calls。
  6. 做可重复验收：固定短对话、两轮记忆、4K/8K 长提示、10 轮稳定性、温度、内存峰值、NPU 利用率和回答接地性。

# 检查服务（不显示凭据）

# 在 MT200 上检查模型列表

# 本机 SSH 隧道
ssh -N -L 127.0.0.1:3080:127.0.0.1:3080 mt200

# 获取本次 dsh 启动生成的 URL；不要提交输出中的 token

ssh mt200 'cat /sys/class/thermal/thermal_zone*/temp'
会话规则：每次 profile 或模型发生变化后必须新建会话。现有会话会保留 preset/model 选择和历史消息；旧会话可能继续携带已经超预算的系统提示。1024-token 版本连续几轮后也可能再次溢出，应主动新建会话。
