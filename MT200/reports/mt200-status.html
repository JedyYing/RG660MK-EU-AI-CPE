4. MT200 的 NPU：从「不可用」到「已实测 12 tok/s」

更正：我最初的结论是「NPU 不可用」，这是错的。真实原因是只测了 llama.cpp 的 ggml-hexagon 通道（它加载自编译的未签名 HTP skel，被安全启动拒绝，错误 0x80000406）。MT200 上装有完整 Qualcomm QNN/AI-RT 2.39 与签名 skel，走 QNN 这条路 NPU 是活的。
  • 官方校验通过：qnn-platform-validator --backend dsp --testBackend → Unit Test on the backend DSP: Passed（HTP V73）。
  • 7B 模型在 NPU 上出字：deepseek-7b QNN bundle，Genie 1.13，输出通顺中文。
  • QNN profile 实测：初始化 7.11 s（每次进程）、prompt 处理 25.2 tok/s（28 token 短 prompt）、TTFT 1.11 s、生成 188 token @ 12.09 tok/s。
  • 已封装为 OpenAI 兼容接口：http://10.42.0.81:8090/v1（模型 deepseek-7b-npu），从 ThinkPad 直连调通，一次问答 11.1 s。
  • 上下文翻倍：模型配置写的是 context_size: 1024，dialog 只给了 512；改为 1024 后 681 token 的 prompt 正常返回，prefill 达 607.9 tok/s。

三、200 TOPS 压榨实验（本轮重点）

3.1 先算清「用掉了多少算力」

单序列自回归推理是访存受限，不是算力受限。按每 token ≈ 2×激活参数 FLOP 折算：

阶段实测速率折合算力占 200 TOPS 峰值
LLM decode12.24 tok/s0.06–0.17 TOPS0.03%–0.09%
LLM prefill（681 token）607.9 tok/s2.9–8.5 TOPS1.5%–4.3%

区间下限按 2.4B 激活参数（V2-Lite 类）估算，上限按 7B dense 估算；bundle 的 n_vocab 102400 / bos 100000 指向 DeepSeek-V2-Lite 系列。

3.2 逐项压榨：哪些有效、哪些无效

尝试结果说明
vtcm_mb: 8无变化（184.1/12.32）VTCM 由图的编译期决定，运行时改不动
num_hvx_threads: 4无变化（184.1/12.35）同上
sustained_high_performance更差 25%（161.4/9.29）突发推理用 burst 才对
两进程并发（LLM）不提吞吐整机 load 冲到 27，sshd 一度失联；DSP 对 LLM 是串行的
--save / --restorerestore 失败每次请求仍要付 7–8.5 s 初始化
context 512 → 1024成功唯一有效的配置项，可用上下文翻倍；2048 加载失败
长 prompt（681 token）prefill 607.9 tok/s固定开销被摊薄，是 prefill 的真实峰值

3.3 换 CNN 负载压吞吐：并发能叠加，但很快撞墙

用 SDK 自带的 yolov8n W8A8（640×640，约 8.7 GFLOP/次）做吞吐扫描，每档 20 次推理/进程：

并发进程总推理数墙钟吞吐折合算力
1201.67 s11.98 inf/s0.10 TFLOP/s
2401.73 s23.12 inf/s0.20 TFLOP/s
4801.85 s43.26 inf/s0.38 TFLOP/s
81602.03 s失败11 条真实错误
163202.17 s失败88 条真实错误
244802.28 s失败169 条真实错误

8 个并发起报错，根因是 FastRPC 会话数上限，不是算力不足：

DspTransport.openSession qnn_open failed, 0xffffffff, prio 100
IDspTransport: Unknown rpc status 0x000003ff
Failed to load skel, error: 1002
结论：这台设备上「能榨出的算力」有明确天花板。
· LLM 单序列：decode 0.06–0.17 TOPS、prefill 2.9–8.5 TOPS；
· CNN 多会话：最多 4 个并发，≈43 inf/s ≈ 0.38 TFLOP/s（约峰值的 0.2%）；再多进程被 FastRPC 会话上限拒绝；
· 混跑/并发均不叠加：LLM 会话串行，LLM+CNN 互相拖慢（CNN 12→4 inf/s）。
· 200 TOPS 是稀疏 INT8、大批量、理想数据复用下的峰值指标，单模型小批量永远到不了。要接近它，需要「大 batch + 高复用」的负载形态（如批量 embedding/分类），而不是跑一个 7B 对话。

3.4 并发与混跑：不能叠加

场景LLM decodeCNN 吞吐整机负载结论
单独 LLM12.43 tok/s—0.7基线
两个 LLM 会话并发12.42 tok/s（第二个失败）—20.0不叠加，DSP 串行
LLM + CNN 同时12.32 tok/s4.02 inf/s（单独 11.98）16.1两边都变差

另外两项也试过：spill-fill-bufsize 32/128/256 该图不支持（加载失败）；mmap-budget 256 无变化（183.9/12.22）；关闭权重共享反而掉 30%（149.7/8.57）。SNPE 运行时在本机不可用（只有主机端工具，报 "No network connection detected"）。

四、当前卡点与下一步

卡点影响解法
NPU bundle context 只有 1024dsh 的 Agent 提示约 2.6K，装不下，NPU 目前只能当独立 OpenAI 服务用用 QNN SDK（x86 主机）按 ≥4K context 重新导出，或向美格索取长上下文 bundle；桥接层已写好，改一行 CONFIG 即可接入
1.5B bundle 加载失败少了一个更快的模型选项其 KV 融成单个 313 MB dmabuf，超过本机可映射上限（CMA 167 MB）；需重新导出或调大 CMA（需改设备树）
FastRPC 会话上限（4）CNN 吞吐卡在 43 inf/s用 batch 而非多进程（当前 bundle 的 batch 维度固定为 1，需重新导出）

建议的下一步（按收益排序）

  1. 拿到 ≥4K context 的 QNN bundle：一步同时解决「NPU 托管 Agent」和「更大上下文」两件事，是本项目最有价值的投入。
  2. 把 NPU 用在对的负载上：批量 embedding / 文档分类 / 图像推理（yolov8n 已验证可用），这类 prefill 密集型任务才吃算力。
  3. ThinkPad 侧维持现有三档：1.7B（17 s/回合，日常）、35B-A3B（60 s/回合，重活）、iGPU 默认开启。
  4. 可选：SYCL 后端（GitHub 带宽不足未测，理论 prefill 可再高）、llama-server 加 --api-key（已完成）。
