# systemd 常驻服务化 — 交付报告
执行者: QRIBuddy · 完成: 2026-08-29

## 定位(重要)
这是把阶段A验证过的解析链封成 PC 上的 systemd 常驻服务, 交付的是"服务框架就绪且能自愈"。
它对真实5G加密流量仍只会报 NO_ACTIVE_STREAM; 真正产出视频指标需阶段B的明文源。
不等于"DPI 在真实业务流量上已上线"。

## 架构决策: 解析侧常驻, 抓包外部喂
遵守用户边界(不写设备公钥/不改authorized_keys/密码只交互一次):
systemd 只常驻解析器, 从命名管道 FIFO 读 pcap 流, 完全不碰 SSH 认证。
抓包由外部推入 FIFO(scripts/feed_fifo.sh: 可灌已有pcap, 或 --ssh 复用手建ControlMaster实时抓)。
这样服务可无人值守常驻, 又不触碰被禁的公钥写入。

## 组件
- src/monitor_service.py     非阻塞FIFO常驻解析器(select轮询, EOF重连, 定期health)
- systemd/rg660mk-video-dpi.service  systemd --user unit 模板(ExecStartPre自动建FIFO)
- scripts/feed_fifo.sh        喂数据脚本(pcap 或 SSH实时)

## 实测验证(均通过)
1. 生命周期: 启动 -> 无流报NO_ACTIVE_STREAM -> 喂流出window指标 -> 断流不退出 ->
   再喂流继续 -> SIGTERM优雅停止(618ms, 无需强杀)。
2. systemd托管: systemctl start/stop 正常; active(running); 内存5.3M/CPU28ms(轻量);
   FIFO由ExecStartPre自动创建; stop后inactive(dead)干净退出。
3. 解析正确性(systemd托管, 单段流): rtp=19782 keyframes=40 completed_idr=320,
   与离线基准完全一致。
4. 跨段流状态隔离: 每段流用全新StreamState, 多段连续喂时各段计数独立正确
   (RG实测流kf=40 / 自测流kf=12)。

## 修复记录(实测中发现并修正)
- 初版FIFO阻塞read导致SIGTERM无法优雅停止 + 无数据时health不触发。
  改用 O_NONBLOCK + select 轮询重构, 两问题均解决。
- 一度观察到 keyframes=43 偏差: 查明是多段流日志追加串扰(测试方法问题),
  非解析bug; 用独立日志干净重验为 40, 确认解析逻辑正确。

## 正式部署方式(需要时)
1. cp systemd/rg660mk-video-dpi.service ~/.config/systemd/user/
2. systemctl --user daemon-reload && systemctl --user enable --now rg660mk-video-dpi.service
3. 开机自启需: loginctl enable-linger $USER (否则登出即停)
4. 喂数据: bash scripts/feed_fifo.sh <pcap>  或  bash scripts/feed_fifo.sh --ssh
5. 看指标: tail -f logs/service_metrics.jsonl
