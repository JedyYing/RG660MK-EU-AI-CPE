# AI CPE 看板：双推理模式 + 八项验收整改（2026-11-02）

## 1. 目标与结论

- 8099 看板支持**两种推理模式**，运行中可切换，无需重启服务：
  - **本地模式**：RG660MK → 笔记本 LAN 代理 → SSH 隧道 → MT200 NPU（deepseek-7b-npu）
  - **在线模式**：RG660MK → Hermes 在线通道（ai.phicotek.com，deepseek-v4-flash）
- 两种模式下 **8 大功能全部可跑通**，本轮实测：两种模式各 **8 项通过 / 0 失败 / 0 未完整验收**。
- 消除"未完整验收"：语音真播报、Immich 真上传、身份识别（新增录入）、板载 LED 三轮内核回读。

## 2. 模式架构

| 模式 | 端点 | 模型 | 链路 | 笔记本是否必需 |
|---|---|---|---|---|
| 本地模式 | `http://192.168.1.244:18091/v1/chat/completions` | `deepseek-7b-npu`（QNN/HTP W4A16，ctx 1024） | RG → 笔记本 LAN 代理(:18091) → SSH -L → MT200(:8090) | 是 |
| 在线模式 | `https://ai.phicotek.com/api/llmrouter/v1/chat/completions` | `deepseek-v4-flash` | RG 出网（4G/WiFi）→ Hermes 同一 provider/key | 否 |

统一入口：`/data/ai_cpe/llm_gateway.py`
- 模式唯一来源：`/data/ai_cpe/local-model-mode.json`（`{"mode": "mt200-local"}` = 本地 / `{"mode": "hermes"}` = 在线）
- 返回 `(text, meta)`，meta 只含 `backend/label/model/elapsed_ms`，页面直接展示，便于追溯
- 安全：固定端点、禁代理、禁重定向、按模式主机白名单；在线 key 只从 `/data/hermes/.hermes/.env` 读取，不入日志、不回传页面

### 为什么本地模式不直连 DSH

`127.0.0.1:3081` 是 MT200 上 dsh 0.2.1 的 **Web 控制台**（转发到 MT200:3080）：
- 根路径 401，`/v1/models` 404 —— 不是 OpenAI 兼容推理 API
- 当前 `dsh headless` 报 `MISSING_CREDENTIAL`（LOCAL_LLM_KEY 未配），本身跑不动推理
- 它自己配置的 provider 就是 `http://127.0.0.1:8090/v1` 的 `deepseek-7b-npu`

因此本地模式直连 8090（与 DSH 同一个模型，链路更短、证据可核），DSH 控制台在看板留入口链接。

## 4. 接口

```
GET  /mode                       → {mode,label,backend,model,endpoint,dsh_console,key_present?}
POST /mode    {"mode":"local"}   → 切本地（等价 "mt200-local"）
              {"mode":"online"}  → 切在线（等价 "hermes"）
POST /run     {"full":true}      → 完整验收（真播报/上传/点灯）
              {"full":false}     → 静音自检（QA 用，UI 不再暴露）
POST /face/enroll {"subject_id":"self"}  → 抓拍当前画面并录入身份模板
POST(ai_service) /vision/enroll  {"subject_id":"self","input":{"path":"..."}}（X-AI-Service-Token）
```

## 8. 已知边界

- 本地 7B（W4A16，1024 ctx）单轮问答约 9–10s，40 token 级 JSON 生成约 20s+：因此工具分类改为确定性路由，模型只负责自由问答
- 身份识别依赖正脸模板：需在摄像头前点一次「录入身份」；模板可重复录入以提升不同角度命中率
- 完整验收会真播报、真开关板载 LED、真上传一张照片到 Immich
- 在线模型偶发复读/口误（如"有什么可以1我可以帮你的吗"）属模型侧，不影响链路判定

## 9. 追加纠正（2026-11-02 下午）：第 5 项「智能家居控制」改判 **fail**

现象：看板显示"本轮检查通过"，但指标里执行器是 `board-led`、`proxy=true`、备注"Matter实灯未验收"。
原因：判定只看"控制面 + 板载 LED 三轮内核回读"，没有校验执行器是否为真实灯具——把演示代理当成了功能实现。

纠正后的口径（已上线）：
- 执行器为 `board-led`（proxy=true）时，第 5 项一律 **fail**，detail = "仅板载LED演示代理（proxy=true），未控制真实灯具 → 智能家居控制未实现"
- 板载 LED 的回读仍作为"控制面自检"证据保留在 metrics 里
- 只有真实执行器（Matter node / 涂鸦灯）三轮回读通过才判 pass

真实灯现状（现场实测）：
- MOES 灯泡 `20:f1:b2:5b:f4:9a` 仍关联在 ra0（-79 dBm），但 **无 DHCP 租约、ARP FAILED、ping 100% 丢包**，IP 不可达；本地 Tuya UDP 协议未开放
- Matter KVS 为空（`/data/ai_cpe/matter/kvs/` 无配网记录）；config.json 里 `node_id=null`
- 设备上没有 `TUYA_ACCESS_ID/SECRET`

要变成真实通过，二选一：
1. **涂鸦云**：把 Access ID/Secret 写入 `/data/hermes/.hermes/.env`（或临时环境变量），恢复 `openapi.tuyacn.com` 控制（DEVICE_ID `6cef15216413d61f09c6u3`），并在 smarthome agent 里加 tuya driver
2. **Matter 本地**：让灯泡进配网模式（断电重启/按开关进入 pairing），用 `sh /data/ai_cpe/services/smarthome/matter_commission.sh <node_id> <setup_pin>` 重新配网，config.json 填 node_id 后自动切 Matter 真灯
