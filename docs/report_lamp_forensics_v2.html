先更正：上一版（11-19 上午）的结论是错的，本报告予以撤回。 上一版把根因判为"灯固件 mDNS 资源泄漏"，依据只是 CHIP Error 0x00000032 Timeout 这段错误文本。 按指令要求补做 tcpdump 抓包后发现：灯在 5.1 毫秒内正常应答了 mDNS，chip-tool 直读 5 秒成功。 那段错误文本来自 MQTT 的 retained（保留）状态消息，是历史失败的残留，不是实时探测结果。 这正是"不能只凭 CHIP 0x32 判断灯固件故障"的实例。

结论摘要

结论 1（已证实）｜灯侧当前完全健康。 抓包（13:16:43）：CPE 发出查询 → 灯 5.1 ms 后应答，SRV / TXT / A / AAAA 四条记录齐全； 同刻 chip-tool onoff read on-off 22 1 5 秒返回成功。灯没有 mDNS 故障，也没有掉线。
结论 2（已证实）｜直接原因是控制进程 smarthome-agent 不存在，且不在 procd 监管中。 /proc 全表扫描无 agent.py；ubus call service list 里只有 smarthome-broker（pid 15055，running），根本没有 smarthome-agent 这一项。 MQTT 的 rg660mk/bulb/set 没有订阅者，控制链路断路。
结论 3（已证实）｜"灯离线"是观测假象，机制是读到了陈旧的 retained 消息。 上层 smarthome.py status 走 MQTT 请求-应答：agent 在时它发布实时状态；agent 不在时， 它只能读到 broker 上 retained 的最后一条状态（内容正是那次 chip-tool 超时的错误文本）， 于是把"没人应答"显示成"Matter 无响应"。这解释了为什么故障描述一直指向灯。
结论 4（待验证）｜灯侧是否存在间歇性 mDNS 退化，仍不能排除。 08:07 那次失败发生时，agent 日志显示它仍在运行（日志持续写入到 12:40），所以当时确有真实超时； 但此后到现在灯一直健康。关键未知项：这期间是否有人给灯断过电——若是，则 08:07 属于灯侧问题； 若不是，则需继续观测。这一点需要你确认。

判定问题证据与结论
ACPE 是否发出 mDNS 查询？是。源 192.168.1.1:55399 → 224.0.0.251:5353；同时发 IPv6 版（ff02::fb）。查询名为 FD330BEA7EEE2496-…0016，与 node 22 对应。
B灯泡是否收到查询？是（间接证明）。同一时刻灯即发出针对该查询名的应答，且 TTL 255、组播标志位符合规范。
C灯泡是否返回响应？是。192.168.1.134:5353 → 192.168.1.1:55399，单播应答（回应 QU 位），携带 SRV/TXT/A/AAAA 四类记录。
D响应是否到达 CPE？是。抓包点即在 br-lan 上，目的地址就是 CPE 的临时端口 55399，UDP 校验和正常（udp sum ok）。
ECPE 是否解析成功？是。同次 chip-tool 5 秒返回，进入正常关机流程（Inet Layer shutdown / FabricTable Shutdown），未出现 0x32。
五问全过 = 灯侧 mDNS 链路完好。 这一条同时否掉了"灯固件 mDNS 资源泄漏"作为当前故障的解释。 上一版报告的错误就出在跳过了这一步：把应用层错误字符串当成了设备侧证据。

四、直接原因链（因果闭合）

① agent.py 进程消失（/proc 无、procd 无条目）
        ↓
② MQTT 主题 rg660mk/bulb/set 无订阅者 → 控制命令无人执行
        ↓
③ smarthome.py status 只能读到 broker 上的 retained 消息
   （内容 = 上一次失败留下的 "CHIP 0x32 Timeout" 文本）
        ↓
④ 上层把"无人应答"呈现为"Matter 无响应 / 灯泡离线"
        ↓
⑤ 演示第 5 项 fail/skip；而灯本身 ping、WiFi、mDNS 全部正常
        ↓
⑥ 人工"断电重启灯"看似有效 —— 因为重启期间 agent 常被顺带重启/恢复
⑥ 是这条链里最值得警惕的一环："断电重启灯"之所以屡屡奏效，可能并不是因为灯需要重启， 而是因为整个控制链在那一两分钟里被重新拉起。这解释了为什么这个"故障"总带着"重启就好"的错觉。
