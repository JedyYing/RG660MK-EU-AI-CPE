二、智能音箱无响应

2.1 现象

对音箱说"你好，小皮"多次无任何回应；有时表现为"要喊两次才应"，有时是"完全没反应但飞书正常"。同一句现象背后，本周实测到 4 种完全不同的根因。

2.2 分层定位方法（按顺序，逐层排除）

层判据本周命中
① 进程/心跳voice_assistant 在？/tmp/voice_hb 是否 2–6 秒前进？11-16 19:23 命中：心跳停滞 → 休眠死锁
② 麦克风能量RMS p50/peak；正常环境音 p50 70–150，人声峰值 >100011-17 09:20 命中：CM564 p50=31/peak=325 → 静音
③ 音频读取完整性心跳前进但无 [miss] 日志 = 帧被截断11-17 09:40 命中：os.read 短读 → VAD 永不完成
④ ASR 文本voice.jsonl 里的 asr= 是否接近唤醒词11-17 11:49 命中：转写成"好小皮"，丢了"你"
⑤ 唤醒词匹配is_wake/strip_wake 对该文本是否为 True同上：三处正则都不认"好小皮"

2.3 四个根因与处置

根因证据处置回滚
① 休眠死锁
（11-16 19:23）		arecord utime 6 ticks 4 秒零增长；主线程 do_select；日志停在 asr="小皮休息"。根因：vad.py 的 proc.wait() 在 arecord 不可中断时永久阻塞所有 wait 加超时；帧循环写心跳；voice_guard 每 2 分钟检查，心跳 >180s 才重启，每小时≤3 次vad.py.bak_*
② CM564 静音
（11-17 09:20）		30 秒录音 p50=31、peak=325，无一帧达 VAD 阈值 450；同期增益 191/75%、开关 on；C270 同环境 rms=387/peak=7837采集切 C270（plughw:CARD=WEBCAM,DEV=0），写入 voice_rec_dev 统一启动路径；增益 50%（18dB）改回 plughw:2,0；换线/换口后复测
③ os.read 短读
（11-17 09:40，修复引入的回归）		心跳前进、RMS p50 500–1500，但 voice.jsonl 一条 [miss] 都没有。原因：os.read 只返回半帧，len(chunk)<frame_bytes→break 每次掐断录音新增 _read_exact()（select 3s 超时 + 循环读满一帧）；修复后 09:47:16 立刻恢复 miss asr=...（ASR 0.5s）vad.py.bak_readexact_*
④ 唤醒词被截断
（11-17 11:49）		日志实锤：{"kind":"miss","asr":"好小皮"}——声学与 ASR 都正常，只丢了开头"你"；原正则要求"你好/小皮"开头，故不匹配加 _wake_norm()：好小皮/好小屁/好下皮 自动补"你"；is_wake / is_sleep_wake / strip_wake 三处统一。自测：好小皮=True、你好小皮=True、小皮=Truevoice_assistant.py.bak_wakenorm_*

三、RG660MK 5G 掉网

3.1 现象与现场

ifstatus wan      → up=False
ip addr           → ccmni0–16 全部 DOWN
ip route          → 无默认路由
nslookup open.feishu.cn → REFUSED
curl open.feishu.cn     → 000
网关日志 09:01:57–09:02:29 连续三次 HTTPSConnectionPool(...:443) Max retries exceeded

恢复后：ccmni2 重新拿到地址（本周见过 10.130.16.222/29、10.36.125.234/29、10.142.191.26/29 等），默认路由恢复，飞书 404/292ms。IP 每次不同，说明是重新拨号而不是原连接恢复。

3.2 分析

层面结论
链路层ql_datacall 数据呼叫消失；重拨可恢复 → 排除 SIM 欠费/无信号（有信号时也会掉）
影响面飞书、在线大模型、ZeroTier 全部依赖 WAN，掉线时一起不可用；本地 8099 与局域网仍可用（无大模型模式不受影响）
恢复阶梯ifup wan → /etc/init.d/mipc_wan.init restart → AT+CFUN=1,1（经 ttyGS0） → 整机重启。重启模组常把整机带重启（uptime 归零），需谨慎
驱动层线索dmesg 中每个发往 ccmni 的包都打印 [ccci1/net]skb_headroom(32) < ccci_header(16)+18（ping、zerotier-one 均命中），约 0.4 条/秒；25 分钟内核内存采样（6 点）未见泄漏（MemAvailable -1MB、Slab +0.2MB）
频率24h 探测只完成 6.5 小时（09:42–16:13），期间 wan_up 全为 1、未捕获掉线，因此无法给出掉线频率
待验证假设（不写成结论）：① 模组固件在特定小区/信号条件下丢失 PDP；② ccci 驱动的 skb 处理异常导致数据面挂死；③ 供电/温度瞬态。缺的是掉线瞬间的模组状态（注册状态、信号、数据呼叫、mipc 进程），应用层日志不足以定位。

3.3 下一步取证

  • 低负载 wan_watch（30 秒）：掉线瞬间落盘 dmesg 尾 120 行、路由、mipc 进程、conntrack，并记录掉线起止时长
  • 只读 AT 查询（以该固件支持为准，确认不争用管理通道）：注册状态、信号、数据呼叫
  • 恢复阶梯加超时、退避、次数上限，禁止无限重启；重启模组前先回传证据

四、本机与 RG660MK 网线不通

4.1 现象

本机打开 http://192.168.1.1:8099/ 打不开，SSH 报 kex_exchange_identification: Connection reset by peer；但 ping 192.168.1.1 有回应（RTT 6–100ms）。ZeroTier 地址 172.25.25.224:8099 同时打不开。

4.2 定位过程与根因

检查结果含义
本机接口enx00e04c557598 不在 ip addr 里；无任何 192.168.1.x 地址USB 网卡从系统消失（拔线时连带脱落/被拔出）
到设备的路由ip route get 192.168.1.1 → via 10.83.96.1 dev wlp0s20f3流量被送到办公网网关，由别的设备回 ICMP
ARP192.168.1.1 在 docker0/br-*/enp1s0 上均为 INCOMPLETE本机根本没有到设备的二层路径
板端对照健康日志同期：sshd/web/mqtt/asr/demo 全部 listen=1，MemAvailable 650MB，uptime 连续设备一直正常；"全灭"是观测侧假象
恢复重插 USB 网卡后：192.168.1.212 出现、8099=200、RTT 0.9ms确认根因
为什么容易误判：拔掉 USB 网卡后，本机仍能 ping 通 192.168.1.1（办公网里另有设备响应），于是"ping 通但端口全关"看起来像设备服务崩了。实际是探测目标根本不是设备。

4.3 改进

  • 监控新增外部路径探测：板子每 30 秒主动访问本机 192.168.1.212:2283，失败且本地 8099 正常时落盘 ext_unreachable 快照，区分"设备本地正常"与"链路不可达"
  • 演示前检查固定先验证本机是否存在 192.168.1.x 接口、路由是否指向 enx*，再判断设备
  • 演示建议全程插着 USB 网卡与网线；ZeroTier 作为备份而非主入口
