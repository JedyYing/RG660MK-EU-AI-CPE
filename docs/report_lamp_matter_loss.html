智能灯泡"必须断电重启"专题分析报告

从 3 次有据可查的失联，到「灯侧 mDNS 失活 + CPE 侧逐命令重建会话」的双层根因
对象：Matter 智能灯泡 d8:fc:92:b8:b1:41 · node_id 22　　承载设备：RG660MK-EU（OpenWrt，MT7992 WiFi）
执行者：应金栋（Jedy Ying）　　证据窗口：2026-11-16 至 2026-11-19　　数据来源：板端日志、chip-tool 回显、压测 CSV

结论摘要

结论 1（已证实）｜灯没有"死机"，是在 Matter 的地址解析层失联。 故障时灯仍 ping 通（3.39 ms）、WiFi 仍关联（−69 dBm）、mDNS 组播路由与组播成员均正常； 唯独 chip-tool 报 CHIP Error 0x32: Timeout @ AddressResolve_DefaultImpl.cpp:124—— 即"问不到灯的 mDNS 地址"。所以断电重启之所以有效，是因为它重启的是灯里的 Matter 协议栈，不是网络。
结论 2（已证实）｜CPE 侧的控制链路把所有鸡蛋放在一个篮子里。 agent.py 的注释自述「每次约 4–5 秒」——每条开关命令都新起一个 chip-tool 进程， 等于每条命令都重新做一次 CASE 握手 + 一次 mDNS 解析。正常态因此要 18.8 秒/项； 一旦 mDNS 应答失效，每条命令都失败，且失败得很慢（37–44 秒）。
结论 3（已证实，已修复）｜演示验收代码有 3 个真 bug，曾把"慢"判成"坏"。 观察窗只有 6 秒（而灯的回执自述滞后 5–25 秒）、恢复路径无预算上限（最坏 17 分钟）、 探针被自己掐断时误判为 fail 而非 skip。三处已按板上最新版重建并上机验证。
结论 4（待验证假设）｜灯固件内部的 mDNS 应答器"用久了不再应答"。 观测到的两次有效存活窗口都在 1 天量级（本次 11-18 07:50 断电 → 11-19 07:00 失联，约 23 小时， 其间完成 300+ 次开关）。这更像时间累积的资源泄漏，而不是单纯的操作计数。 无法直接证实的原因：灯不可登录、无灯侧日志，只能从外部行为反推。

三、根因分析（分层）

3.1 主因层：灯侧 Matter/mDNS 应答器失活　待验证假设

故障时灯"能 ping、能关联、不应答 mDNS"。能 ping 说明 IP 栈正常；不应答 mDNS 说明 Matter 协议栈里的服务发现模块已经不再工作。这一层在灯内部，我们无法登录、也没有灯侧日志， 因此只能给出行为级结论与可证伪的假设：

  • 假设 A（最可能）：mDNS 应答器长期运行后 socket / 定时器资源未释放，达到上限后不再响应查询。特征是与运行时长相关，与操作次数弱相关——与本次"约 23 小时后失效"吻合。
  • 假设 B：灯固件在长时间高频开关后进入某种降级状态（例如 CASE 会话表项泄漏）。11-18 当天 300+ 次开关后仍正常，到次日清晨才失效，支持"泄漏缓慢累积"而非"当场崩溃"。
  • 假设 C（较弱）：路由器侧组播抑制导致灯"忘记"向组播组注册。但本次 br-lan 的组播路由与成员都在，且同一网段另一台设备（14:90:7a）工作正常，可以基本排除。

3.2 放大层：CPE 逐命令重建 chip-tool 会话　已证实

控制链路是：演示页 → MQTT（本机 1883）→ services/smarthome/agent.py → 每次调用 chip-tool。 agent 源码注释明确写着「每次约 4–5 秒」，且每次命令都是新进程，意味着每条命令都要 重新做一次 CASE 握手和一次 mDNS 解析。

实测：一次"关→开→恢复"共 3 条命令 → 正常态 18.8 秒（约 6 秒/条）
      卡死态 37–44 秒 → 每条命令都在等 mDNS 解析超时

后果有两条：① 正常情况下第 5 项就要吃掉 18.8 秒，是整轮演示里最慢的一项； ② 一旦 mDNS 失效，每条命令都要独立失败一次，故障被放大 3 倍（这就是"感觉等了半天没反应"的直接来源）。

3.3 诱因层：无线链路质量不均衡　待验证假设

灯的四条链 RSSI 为 −83 / −67 / −41 / −83，两条链 SNR 只有 4 和 0；上行 7.1% 的包失败。 mDNS 走的是低速率组播，对丢包和空口占用比单播敏感得多。我们无法证明这是触发因素， 但它会显著放大"偶发解析不到"的概率，属于应当消除的风险项。

3.4 观测层：验收代码 3 个 bug 把"慢"判成"坏"　已证实，已修复

Bug后果修法（已上机）
观察窗只有 6 秒（tries=3 × gap=2s）灯回执自述滞后 5–25 秒，慢灯被误判"power 未收敛"——11-18 压测第 36 轮那次失败即此因观察窗改为 28 秒，且受单项总预算约束
恢复路径 t=90 / tries=10 无上限最坏情况下单这一项可拖约 17 分钟，足以拖垮整场演示改为 t=30，等待时间受剩余预算约束
探针被自己掐断时错误文本里没有"超时"字样灯明明无响应，却被报成"控制面初态无效"的 failrc≠0 直接判为 Matter 无响应，归入 skip 并给出准确结论

五、解决方案

5.1 立即措施（演示保障，今天就能做）

#动作说明效果
A1灯断电 10 秒再上电已验证有效；恢复的是灯内 Matter 协议栈立即恢复，但只保约 23 小时
A2演示当天早上做一次断电把"剩余寿命"重置到最大，覆盖当天演示窗口可把风险压到最低
A3演示顺序把第 5 项放最后若真出问题，不阻塞前面 9 项降低观感损失

5.2 工程加固（本周，可自动化，推荐）

#措施做法收益
B1看门狗自动复位连续 2 次 mDNS 解析超时 → 通过可编程插座给灯断电 5 秒再上电；不依赖人工把"人工重启"变成"自愈"，故障窗口从小时级降到分钟级
B2chip-tool 会话复用改用 chip-tool 交互模式常驻，命令走同一条 CASE 会话，不再每条命令重连单条命令从 4–5 秒降到 1 秒内，第 5 项整体可进 10 秒
B3mDNS 解析结果缓存解析成功后缓存 60 秒，减少解析次数减少对灯 mDNS 的依赖频率
B4灯固定 IP + 静态 ARP 绑定消除 ARP STALE 带来的首包丢失去掉一类偶发抖动
B5改善灯的无线位置当前两链 −83 dBm、SNR 0–4，属明显偏弱；调整位置或加一个 AP降低组播丢包率
B1 + B2 是性价比最高的组合。B1 解决"灯会失效"这个事实，B2 解决"失效后反应太慢"这个体验； 两者都不需要动灯固件，也不需要换硬件。做完之后，即使灯每天仍会失效一次， 演示页也只会在某一轮出现一次 skip，而不会出现 40 秒的等待。
