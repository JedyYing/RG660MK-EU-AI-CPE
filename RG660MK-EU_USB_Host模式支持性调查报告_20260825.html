1. 执行摘要与最终判定

1.1 一句话结论

RG660MK-EU 在本机现有固件和载板描述下支持 USB Host/USB 双角色能力；但当前端口处于 Device 模式，不能据此宣称 USB Host 已经可用，更不能宣称 USB 算力棒链路已通过。

1.2 为什么可以判定“具备 Host 能力”

  1. 被测模组内核设备树把实际绑定的控制器 usb@11591000 声明为 dr_mode=otg，并声明 maximum-speed=super-speed-plus、mediatek,usb3-drd 和 usb-role-switch。
  2. 同一控制器节点下存在 compatible=mediatek,mtk-xhci 的 xHCI Host 子节点。xHCI 是 Host 控制器路径，不是纯 Gadget 路径。
  3. 运行内核配置为 CONFIG_USB_MTU3_DUAL_ROLE=y、CONFIG_USB_XHCI_HCD=y、CONFIG_USB_ROLE_SWITCH=y；没有选择 Host-only 或 Gadget-only，而是明确选择双角色。
  4. 板级设备树存在固定 5 V vbus regulator，且控制器存在 VBUS consumer 关系；这表明固件为 Host 供电路径建模，而非只有 Device 受电路径。
  5. 设备树包含状态为 okay 的 TI HD3SS3220 Type-C DRP/SuperSpeed MUX 节点，并通过 endpoint 与 USB 控制器相连。TI 官方将该器件定义为 Type-C 双角色端口控制器。
  6. Linux 5.15 上游 MTU3 驱动的 Kconfig、设备树 binding 和驱动实现与上述实机配置相互印证：Dual Role 同时启用 Host/Gadget；Host 基于 xHCI；切入 Host 时切换端口并启用 VBUS。

1.3 为什么不能判定“当前 Host 已可用”

  • 模组运行态文件 /sys/devices/platform/11591000.usb/role_mode 返回 device。
  • UDC 为 configured，当前速度 high-speed；本机通过 ADB/RNDIS/ACM 把模组当作 USB 外设。
  • 模组侧没有 Host root bus，也没有任何下游 USB 设备 VID:PID/速度记录。
  • 5 V VBUS regulator 当前为 disabled、num_users=0，与 Device 角色一致。
  • HD3SS3220 I²C 节点当前没有绑定驱动，且 /sys/class/typec 没有端口对象；自动角色检测/切换链路仍有风险。
  • 未在带外管理、有源 Hub 和测试外设条件下执行 Host 切换。贸然切换很可能中断当前 ADB 管理链路。
最终状态标签：
能力层：SUPPORTED（支持）；当前运行态：DEVICE（非 Host）；实际外设验收：BLOCKED（待受控实测）。

4. 关键证据分析

4.1 当前链路为何不是“模组 Host”

Bus 001 Device 017: ID 2c7c:0710 Quectel RG660MK-EU
/:  Bus 01 ... Driver=xhci_hcd/12p, 480M
    |__ Port 5: Dev 17 ... Driver=rndis_host, 480M
    |__ Port 5: Dev 17 ... Driver=cdc_acm, 480M
    |__ Port 5: Dev 17 ... Driver=usbfs, 480M

模组内部：
role_mode=device
UDC state=configured
UDC current_speed=high-speed
Host buses=NONE
Enumerated downstream devices=NONE

rndis_host 是 Ubuntu PC 上的驱动名称，其中的 “host” 指 PC 作为 Host 驱动 RNDIS 外设，不表示 RG660MK-EU 是 Host。PC 侧 root hub、模组侧 UDC configured、模组侧 role_mode=device 三项形成方向一致的直接证据。

4.2 Device Tree 不只是“泛泛的 OTG 字样”

/proc/device-tree/usb@11591000
  compatible=mediatek,mtu3
  dr_mode=otg
  maximum-speed=super-speed-plus
  mediatek,usb3-drd   (flag)
  usb-role-switch     (flag)
  mediatek,force-vbus (flag)

/proc/device-tree/usb@11591000/xhci0@11590000
  compatible=mediatek,mtk-xhci

这组属性共同指向双角色 Host 实现，而非仅仅一个可疑字符串：dr_mode=otg 指定双角色；mediatek,usb3-drd 指示 USB3 端口参与 dual-role；usb-role-switch 指示角色切换框架；xHCI 子节点是 Host 控制器实例。Linux 5.15 MTU3 binding 明确说明 Host 基于 xHCI，并规定在 Host 模式启用时应有 xHCI 子节点。

4.3 内核不是 Gadget-only

CONFIG_USB_SUPPORT=y
CONFIG_USB_XHCI_HCD=y
CONFIG_USB_MTU3=y
# CONFIG_USB_MTU3_HOST is not set
# CONFIG_USB_MTU3_GADGET is not set
CONFIG_USB_MTU3_DUAL_ROLE=y
CONFIG_USB_GADGET=y
CONFIG_USB_ROLE_SWITCH=y
CONFIG_TYPEC=y
CONFIG_TYPEC_HD3SS3220=y

“Host-only 未选中”不能解释为“不支持 Host”。MTU3 的三个模式是互斥选择：Host-only、Gadget-only、Dual Role。当前明确选择 DUAL_ROLE；Linux Kconfig 对该项的定义是 Host 与 Gadget 两种功能均启用。因此，内核能力层判定为 Host-capable 是成立的。

4.4 VBUS 供电路径的意义与限制

DT: /proc/device-tree/vbus_regulator
  compatible=regulator-fixed
  regulator-name=vbus
  regulator-min-microvolt=5000000
  regulator-max-microvolt=5000000
  enable-active-high

Runtime:
  name=vbus
  type=voltage
  microvolts=5000000
  state=disabled
  num_users=0

USB Host 不仅要发起总线事务，还通常需要向下游提供 VBUS。实机固件已建立 5 V regulator 及控制器 consumer 关系，支持“板级设计考虑了 Host VBUS 控制”的判断。当前 VBUS 关闭是 Device 模式的正常表现，但尚未验证切 Host 后 GPIO、5 V 电源、限流和过流保护是否真实工作，也没有测量可供电电流。因此不能由该节点推导“可直接给 NPU 供电”。

4.5 Type-C 双角色设计与当前异常点

Device Tree:
  /i2c@10f90000/hd3ss3220@47
  compatible=ti,hd3ss3220
  status=okay
  endpoint <--> usb@11591000/port/endpoint@2

Runtime:
  /sys/bus/i2c/devices/4-0047 存在
  driver link: UNBOUND
  /sys/class/typec: 无端口对象

TI 官方资料将 HD3SS3220 定义为 USB Type-C DRP 控制器和 SuperSpeed 2:1 MUX，支持最高 10 Gbps。因此节点设计意图与 USB 双角色一致。但本次没有驱动绑定，自动 CC 检测、方向 MUX 和 Host/Device 角色通知是否工作不能确认。这是当前从“具备 Host 能力”走向“可稳定使用 Host”的主要风险点之一。

4.6 SuperSpeed 证据应如何解释

Ubuntu 历史 kernel journal 多次记录同一 VID:PID/序列号以 new SuperSpeed USB device 枚举，证明模组作为 Device 时，至少在此前连接条件下，USB3 物理链路曾经成立。当前采样则是 480M，说明速度会受线缆、插口方向、连接状态、MUX 或启动状态影响。该历史记录不能替代“模组作为 Host 时下游设备达到 5000M/10000M”的证据。

5. 反证、矛盾与未决风险

现象是否反驳 Host 支持正确解释
当前 role_mode=device否反驳“当前正在 Host”，不反驳双角色控制器可切 Host。
CONFIG_USB_OTG 未启用不足以反驳本平台的角色切换由 MTU3 DRD 与 USB_ROLE_SWITCH 路径实现；决定性配置是 USB_MTU3_DUAL_ROLE=y。
无 Host root bus反驳当前 Host当前为 Device，xHCI Host 未处于活动枚举态；这正是为什么运行态验收仍为 BLOCKED。
VBUS disabled反驳当前 Host 供电与 Device 角色一致；尚需受控切换后测量 5 V、电流与保护。
HD3SS3220 未绑定不反驳控制器能力，但降低可用性置信度可能导致自动角色/方向切换不工作；必须查固件驱动绑定或采用厂商支持的切换方式。
当前仅 480M不反驳最高速率能力UDC 的 maximum_speed=super-speed-plus 且历史曾以 SuperSpeed 枚举；当前会话速度不等于控制器上限。
未找到 RG660MK-EU 官方 Hardware Design形成文档缺口实机配置证据很强，但无法独立核验模块引脚、电气限值、推荐 VBUS/CC 设计和厂商支持边界。

5.1 不得作出的过度结论

  • 不得把 super-speed-plus 的 DT 上限直接写成“当前 Host 10 Gbps 已通过”。
  • 不得把 PC 上的 rndis_host 驱动名写成“RG660MK-EU 正在 Host”。
  • 不得把 5 V regulator 节点写成“供电能力足以驱动算力棒”；电流能力和瞬态尚未测量。
  • 不得把 HD3SS3220 的器件规格直接当作整个载板端到端 10 Gbps 保证，特别是该节点当前未绑定驱动。
  • 不得宣称所有 RG660MK-EU 产品形态都支持同样接口；本报告只覆盖此序列号、此固件和此 CPE/EVB 载板。

6.2 对用户问题的最终回答

若“支持 USB Host 模式”指模组控制器、当前内核和当前板级固件是否包含 Host 能力，答案是支持，证据达到高置信。

7. 安全验证方案与验收标准

7.1 前置条件

  1. 先建立不依赖该 USB 口的 RJ45 SSH 或 DB9/UART 控制台，并验证断开 USB 后仍可登录。
  2. 取得当前载板原理图/端口图和 RG660MK-EU 官方 Hardware Design，确认目标连接器、VBUS GPIO、CC、SuperSpeed TX/RX、限流和过流保护。
  3. 确认 Quectel/固件供应方支持的 role 切换接口。不要猜测 sysfs 写法；本次可见 role_mode 为只读。
  4. 使用有独立电源的 USB 3.x Hub，避免由模组直接承担算力棒启动浪涌。

7.2 建议测试顺序

  1. 记录 Device 模式基线：role、UDC、VBUS 电压、ADB、网络。
  2. 通过厂商确认的方法切 Host；从带外控制台观察 xHCI、root hub、VBUS 和 dmesg。
  3. 先接低风险 USB 2.0 U 盘/键盘验证基础枚举，再接 USB 3.x U 盘验证 SuperSpeed。
  4. 最后通过有源 Hub 接算力棒；记录准确 VID:PID、设备节点、自身 speed、驱动绑定和 Runtime 识别。
  5. 连续运行至少 30 分钟，覆盖冷插、热插、拔插恢复；检查 reset/disconnect、供电跌落、OOM、watchdog 和 CPE 网络回归。

7.3 Host 运行态 PASS 标准

测试项PASS 条件
角色模组侧可复核为 Host；UDC 不再承担当前数据通道。
Host 控制器出现 xHCI Host root hub 和对应 /sys/bus/usb/devices/usb*/speed。
VBUS连接器实测约 5 V，空载/负载正常，限流与过流保护符合载板规范。
USB 3.x目标外设自身 sysfs speed 至少 5000M；不能只看 root bus 上限。

业务回归5G/WAN/LAN/Hermes 等 CPE 主业务无不可接受回归。
