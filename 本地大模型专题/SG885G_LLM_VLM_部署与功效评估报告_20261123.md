## 一、执行摘要

本次在 SG885G-WF 上部署了两套本地模型服务：

| 服务 | 模型 | 运行设备 | 端口 | 状态 |
|---|---|---|---|---|
| LLM | Qwen2 3B Q4_K_M（`q3.gguf`） | HTP0 | 8080 | 运行中 |
| VLM | Qwen2.5-VL-3B Q4_K_M | HTP0 + CPU（mmproj） | 8081 | 运行中 |

VLM 的文本主干跑在 HTP0，视觉编码器 mmproj 跑在 CPU；v2.1 已通过 `--mmproj-device none` 与 `--no-mmproj-offload` 修复启动崩溃。详见第四节和第十二节。

核心结论：

- **LLM 已实际跑在 HTP0 NPU 上**，实测约 **14.15 tok/s**（3B Q4，上下文 2048）。
- **VLM 已可完成图片理解**，v2.1 修复后文本主干使用 HTP0，视觉编码器使用 CPU，大图约 **29.5 秒/张**。
- LLM + VLM 同时驻留后，系统仍有约 **7.5–7.8 GB MemAvailable**。
- 3B LLM + 3B VLM 是可稳定驻留组合；7B LLM 再叠加 VLM 内存余量不足，本次未部署。

## 四、NPU 算力利用情况

### 4.1 LLM 的确跑在 HTP0 上

`server_htp.log` 关键行：

```text
ggml-hex: device 0: HTP0 (phys=0, virt=0, domain=cdsp:3)
resolve_fused_ops: layer 0 is assigned to device HTP0
```

`llama-bench -dev HTP0 -ngl 99` 实测：

| 测试 | 结果 |
|---|---:|
| pp32（预填充） | 226.86 ± 2.22 tok/s |
| tg16（逐 token 解码） | 15.33 ± 0.03 tok/s |

运行中 chat 实测：

```text
prompt 35 tokens + output 21 tokens
prompt：210.03 tok/s
decode：14.15 tok/s
```

### 4.2 NPU 算术利用率估算

3B 模型每生成一个 token 的粗略前向计算量：

```text
2 × 3.40B 参数 ≈ 6.8 GFLOP/token
```

按 14.15 tok/s 计算：

```text
有效算术吞吐 ≈ 6.8 × 14.15 ≈ 96.2 GFLOP/s
≈ 0.096 TFLOPS
0.096 / 48 TOPS ≈ 0.20%
```

按预填充 226.86 tok/s 计算：

```text
6.8 × 226.86 ≈ 1.54 TFLOPS
1.54 / 48 TOPS ≈ 3.2%
```

> 注意：这是**算术利用率估算**，不是 HTP 硬件占空比。Android 侧没有公开的 HTP 占用率节点，无法直接读取“NPU 使用了百分之多少”。低百分比不代表异常：LLM 逐 token 解码是**内存带宽受限**，不是算力受限。

### 4.3 VLM 的 NPU 状态

v2.1 修复后，VLM 采用混合设备模式：

```text
文本主干（语言模型）：HTP0（Hexagon NPU）
视觉编码器（mmproj）：CPU
```

启动参数：

```bash
-dev HTP0 -ngl 99 --mmproj-device none --no-mmproj-offload
```

实测结果：

```text
prompt 256 tokens：约 27.7 秒
output 24 tokens：约 1.7 秒
decode：约 13.5 tok/s
大图总耗时：约 29.5 秒
```

崩溃历史：如果让 mmproj 走 OpenCL/HTP，加载阶段会出现：

```text
F libc: Fatal signal 11 (SIGSEGV)
#00 libggml-opencl.so
#04 libmtmd.so
```

如果强行让 mmproj 走 HTP，还会出现：

```text
ggml-hex: dspqueue_read failed: 0x0000002e
ggml_abort
```

所以 v2.1 的修复思路是：**文本主干继续用 HTP，mmproj 强制留在 CPU**，从而避开 OpenCL/HTP 视觉编码的崩溃。NPU 不再是 0%，但视觉编码仍是 CPU 瓶颈。

## 五、如何检查部署的功效

### 5.1 进程是否存活

```bash
adb -t 3 shell "ps -A | grep llama"
```

正常应看到两个 `llama-server` 进程：一个 8080（LLM）、一个 8081（VLM）。

### 5.2 健康检查与模型列表

```bash
adb -d forward tcp:28080 tcp:8080
adb -d forward tcp:28081 tcp:8081
curl http://127.0.0.1:28080/health
curl http://127.0.0.1:28081/health
curl http://127.0.0.1:28080/v1/models
curl http://127.0.0.1:28081/v1/models
```

预期：返回 `{"status":"ok"}`，VLM 模型 `capabilities` 包含 `multimodal`。

### 5.3 内存检查

```bash
adb -t 3 shell "grep -E 'MemTotal|MemAvailable|MemFree' /proc/meminfo"
adb -t 3 shell "free -m"
```

关注 `MemAvailable`，不要只看 `MemFree`；Android 会保留大量可回收缓存。

### 5.4 速度检查

```bash
adb -t 3 shell "cd /data/local/tmp/llama && LD_LIBRARY_PATH=. \
  ./llama-bench -m q3.gguf -p 32 -n 16 -t 4 -dev HTP0 -ngl 99"
```

看 `pp32` 和 `tg16` 两列；当前基线约为 226.86 / 15.33 tok/s。

### 5.5 实际请求检查

```bash
curl -sS http://192.168.1.212:19083/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"q3.gguf","messages":[{"role":"user","content":"用一句话介绍你自己"}],"max_tokens":32,"stream":false}'
```

响应里的 `timings.predicted_per_second` 就是本次 decode 速度。

### 5.6 日志检查

```bash
adb -t 3 shell "tail -50 /data/local/tmp/llama/server_htp.log"
adb -t 3 shell "tail -50 /data/local/tmp/llama/vlm_server5.log"
```

重点看：`layer 0 is assigned to device HTP0`、`model loaded`、`listening on`，以及是否有 `SIGSEGV`。

## 九、7B 参数模型扩展可行性（v2.0 新增）

### 9.1 结论先行

**不能简单说“完全可以”。** 7B 是否可用，要分三种情况：

| 目标 | 判断 | 说明 |
|---|---|---|
| 只跑 7B LLM | 有机会，必须实测 | 内存账面可容纳，但 HTP 对 7B Q4 的单次映射可能失败 |
| 7B LLM + 3B VLM 同时驻留 | 不建议 | 预算约 17 GB，超过 14.97 GB 总内存 |
| 7B Q2 + VLM | 可塞入，但不推荐 | Q2 量化质量损失明显，不适合生产 |

### 9.2 7B 单独运行的内存预算

7B Q4_K_M 权重约 4.4 GB，估算：

```text
Android 系统常驻        约 6.5 GB
7B Q4 权重              约 4.4 GB
KV cache / 运行时       约 1.0–1.5 GB
合计                    约 11.9–12.4 GB
总内存                  14.97 GB
```

账面余量约 2.5–3.0 GB，**单独运行有希望，但必须实测**。

### 9.3 7B + 3B VLM 同时驻留

```text
Android 系统            约 6.5 GB
7B Q4 权重              约 4.4 GB
7B 运行时/KV            约 1.5 GB
3B VLM 权重 + mmproj    约 2.9 GB
VLM 运行时              约 2.0 GB
合计                    约 17.3 GB
```

超过 14.97 GB 总内存，**不建议同时常驻**。如果必须两者都用，只能串行加载/卸载，切换会有加载时间，并可能触发 Android 内存回收。

### 9.4 HTP 对 7B 的限制

MT200（QCS9075）上 7B Q4_K_M（4.36 GiB）曾因 `fastrpc` 映射上限无法上 HTP0；SG885G（QCS8550）是否同样受限，**尚未实测**，不能直接假设可用。

建议先运行：

```bash
cd /data/local/tmp/llama
export LD_LIBRARY_PATH=.
./llama-bench -m Qwen2.5-7B-Instruct-Q4_K_M.gguf \
  -p 32 -n 16 -t 4 -dev HTP0 -ngl 99
```

判定：

- 如果正常跑完：记录 pp32 / tg16，再评估是否上线；
- 如果报 `fastrpc` / 映射错误：说明 7B Q4 不能走 HTP，只能考虑 CPU/GPU 或 Q2；
- 如果走 CPU：速度会明显下降，不建议做实时对话。

### 9.5 建议

```text
需要 LLM + VLM 同时在线：保持 3B LLM + 3B VLM
只需要最大参数 LLM：可以测试 7B Q4 单独运行
需要 7B 且要实时：先验证 HTP，不能只看 48 TOPS
```

## 十一、结论与建议

1. **LLM 已可用**：HTP0 上 3B Q4 达到约 **14 tok/s**，适合短对话、意图理解、摘要、轻量工具调用。
2. **VLM 已可用但偏慢**：文本主干 HTP0 + mmproj CPU，约 1–29.5 秒/图，适合低频关键帧理解，不适合实时视频。
3. **NPU 算力利用率不能简单看百分比**：LLM decode 受内存带宽限制，按峰值估算仅约 0.2%；预填充约 3.2%。真正有价值的是 HTP 层卸载与实测 tok/s。
4. **7B LLM 不建议与 3B VLM 同时驻留**：当前 3B + 3B 已占约 7–8 GB，7B 会逼近上限。
5. **下一步**：继续优化 VLM 视觉编码器（当前 mmproj 仍在 CPU）；增加 API Key 与开机自启；把 `sg885g-local` 接入 `llm_gateway`。

## 十二、v2.1 修复记录

### 12.1 问题

VLM 启动时，如果让 mmproj 走 OpenCL/HTP，出现：

```text
F libc: Fatal signal 11 (SIGSEGV)
#00 libggml-opencl.so
#04 libmtmd.so
```

如果强行让 mmproj 走 HTP，推理阶段出现：

```text
ggml-hex: dspqueue_read failed: 0x0000002e
ggml_abort
```

### 12.2 修复

不要在 VLM 上把视觉编码器 offload 到 OpenCL/HTP；保留文本主干 HTP0，强制 mmproj 在 CPU：

```bash
GGML_OPENCL_DISABLE=1 ./llama-server \
  -m Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf \
  --mmproj mmproj-Qwen2.5-VL-3B-Instruct-f16.gguf \
  --host 127.0.0.1 --port 8081 -c 2048 -t 8 \
  --image-max-tokens 256 \
  -dev HTP0 -ngl 99 --mmproj-device none --no-mmproj-offload
```

### 12.3 修复结果

```text
模型正常加载，无 SIGSEGV
prompt 256 tokens：约 27.7 秒
output 24 tokens：约 1.7 秒
decode：约 13.5 tok/s
大图总耗时：约 29.5 秒
```

结论：**启动崩溃已修复；NPU 已参与 VLM 文本推理，视觉编码器仍为 CPU 瓶颈。**
