2026-11-23 的设备环境实测表显示，两台 SG560D 的 adb 实测配置为：


**SG560D-B 实测：**

```text
SoC：QCM6490（soc_id 497）
CPU：4×A55 + 4×A78，最高 2.707GHz
GPU：Adreno 643，kgsl 812MHz
NPU：Hexagon 770，12 TOPS 稠密
内存：3.12 GiB 总 / 约 0.71 GiB 可用
QNN：QNN 2.44 全量包在 /data/local/tmp（net-run / validator）
系统：Android 16
存储：60.3GB UFS，/data 46G 用 44G（96%）
网络：rmnet_data5 10.45.0.21/30；wlan2 10.58.80.35/24
```

**与 SG885G-WF 对比：**

```text
内存：SG885G 14.97GB（约 10.47GB 可用）
      SG560D 3.1–3.2GB（约 0.7–1.7GB 可用）
      → 3B LLM 已很勉强，VLM 基本不可行

NPU：SG885G 48 TOPS INT8；SG560D 12 TOPS 稠密
     → 同模型速度预计低 3–5 倍

GPU：SG885G Adreno 740 v2；SG560D Adreno 643
     → VLM 视觉编码更慢

QNN：SG885G HTP V73 库齐全
     SG560D-A 无 /vendor QNN；SG560D-B 有 QNN 但空间/内存不足
     → QNN 不能直接救场

当前 LLM：SG885G Qwen2 3B 约 14.15 tok/s
          SG560D 预计 4–7 tok/s 或更低
          → 语音对话明显变慢

当前 VLM：SG885G 3B VLM 可运行
          SG560D 3B VLM 基本装不下
          → 不能达到相同效果
```

**评估结论：**

```text
SG560D 不能替代 SG885G 作为主力 LLM/VLM AI Box。
它不是“同档次但便宜一点”，而是内存和算力都低一个档：
- 3B LLM Q4 权重约 1.95GB，Android 系统后剩余空间不足以稳定加载；
- 3B VLM 需要约 3GB 权重 + 视觉运行时，4GB 总内存不可行；
- SG560D-A 没有 /vendor QNN 库，SG560D-B 有 QNN 但可用内存仅 0.71GB、/data 已用 96%。
```

**SG560D 的合理用途：**

```text
SG560D-A：语音前端、ASR/TTS、轻量 YOLO、测试机
SG560D-B：QNN 2.44 轻量验证（先清 /data），1.5B 级小模型
不要用于：3B LLM + 3B VLM 同时驻留、实时语音大模型、高质量图片理解
```

## 四、测评方法

### 4.1 评分规则

- 每题智力得分 0–10 分；
- 10 题合计 100 分；
- 速度指标单独记录，不并入智力分；
- 评分参考：

```text
9–10：完全正确，结构清晰
7–8：核心正确，仅有小瑕疵
5–6：部分正确，有关键缺口
3–4：存在明显错误
0–2：答非所问或自行编造
```

### 4.2 一致性

- LLM：10 题串行，每题独立提问；n_ctx=2048，slots=4；max_tokens=256；服务端默认采样。
- VLM：10 题串行，每题独立提问；900×650 测试图；max_tokens 按题目 20–240；temperature=0.1。
- VLM 的 Q6、Q10 命中图像/前缀缓存，耗时明显偏低；速度统计同时给出原始值和未缓存值。

## 6.5 视频抽帧测试

VLM 本身是**图像模型**，不能直接把 MP4 当作输入；视频理解必须先在端侧或服务端抽帧，再把帧图片送给 VLM。本次补充了一条抽帧链路测试：

```text
测试视频：/data/ai_cpe/vlm_eval_20261123/vlm_test_video.mp4
时长：6 秒，900×650，25 fps
内容：0–2s 场景图 → 2–4s 设备巡检表 → 4–6s 英文警示牌
抽帧点：第 3.0 秒
抽帧文件：video_frame_3s.png
问题：读出 SG560D 的温度与状态，以及 MT200 的温度
```

![VLM 视频抽帧：第 3 秒设备巡检表](/data/ai_cpe/vlm_eval_20261123/video_frame_3s.png)

**VLM 回答：**

```text
根据设备巡检表，SG560D 的温度为 38.2°C，状态为告警。
MT200 的温度为 52.1°C，状态为正常。
```

**结果：** 抽帧内容识别正确，给 **10 / 10**；本次抽帧请求耗时 **28.67 秒**（视觉预处理约 25.4 秒，decode 约 3.2 秒）。

**边界说明：**

- 这是“视频抽帧 + 单帧理解”测试，不是原生视频时序理解；
- VLM 不会自动理解帧间动作、先后顺序和持续变化；
- 真正的视频理解需要多帧采样 + 时序逻辑，当前 3B VLM 不适合做实时多帧推理；
- 实际部署建议：摄像头/视频流 → 抽帧（1–2 fps 或事件触发）→ VLM 单帧理解 → LLM 汇总。

## 八、原因分析

### 8.1 VLM 空间关系错误

第 3 题把蓝色方块判成在左侧，说明：

- 模型对“整体相对位置”的全局空间关系不稳定；
- 物体颜色识别正确，但左右方向映射错误；
- 这类任务需要更明确的坐标/参照物提示，或先用检测模型给出框，再让 VLM 判断。

### 8.2 VLM 计数差值错误

第 4 题合计 5 正确，但“红色比蓝色多几个”回答 2：

- VLM 能数出红 3、蓝 2，但做差值时算错；
- 说明“视觉计数 + 算术”两步组合仍不稳定；
- 应把计数结果先结构化输出，再交给计算器/LLM 算差值。

### 8.3 VLM 格式约束不稳定

第 2 题 JSON 内容正确，但加了 Markdown 代码围栏：

- VLM 的“内容正确”不等于“格式正确”；
- 对严格 JSON 场景，需要在后处理层剥离围栏或使用 JSON schema 校验；
- 不能直接把它接到需要纯 JSON 的自动化链路。

### 8.4 VLM 速度瓶颈

VLM 900×650 图片的视觉编码在 CPU：

```text
视觉预处理：约 27–36 秒/张
文本 decode：约 12 tok/s
```

所以它适合：

```text
离线图片理解
截图 OCR
表格读取
现场图片解释
```

不适合：

```text
实时摄像头全图理解
实时语音对话中的每帧视觉
```

## 九、建议

### 9.1 LLM

1. NB-IoT NTN 等专业概念加知识库/RAG，不直接交给 3B；
2. 排错类问题用结构化模板：可能原因 → 验证命令 → 判定依据；
3. max_tokens 从 256 放宽到 512–1024，复测第 4、5、8 题；
4. 抗幻觉题加入“已知正确陈述”对照组，避免模型过度否定。

### 9.2 VLM

1. 900×650 全图改为 **480×360 或 ROI 裁剪**，可显著降低视觉编码时间；
2. 表格/代码类先做 OCR 或版面分析，再让 VLM 解释；
3. 需要空间关系时，先由 YOLO/检测给出框，再让 VLM 判断相对位置；
4. JSON 输出加后处理：剥离代码围栏、JSON 解析失败重试；
5. 不要用 VLM 替代 LLM 做实时对话；两者分工：
   - LLM：文本推理、格式、对话；
   - VLM：读图、读表、OCR、截图理解。

## 十、总结

```text
LLM：79/100，快，适合文本对话、格式输出、逻辑推理
VLM：79/100，慢，适合读图/读表/OCR，不适合实时全图理解
相同总分，不同能力结构；不能互相替代
```

**推荐落地方式：**

```text
语音/文本问答 → LLM（Qwen2 3B）
图片/截图/表格 → VLM（Qwen2.5-VL-3B）
复杂图片 + 精确计数 → YOLO/OCR 先处理，再交给 VLM
AI Box 主力 → SG885G-WF
SG560D → 语音/视觉前端或轻量 QNN 验证，不替代 SG885G
```
