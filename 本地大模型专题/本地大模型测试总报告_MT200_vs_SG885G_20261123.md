- **版本**：v1.0
- **日期**：2026-11-23
- **生成者**：hermes
- **数据来源**：

## 一、结论摘要

1. **MT200 的对话效果更好，首要原因是模型更大**：MT200 使用 **DeepSeek 7B（W4A16）**，SG885G 当前使用 **Qwen2 3B Q4_K_M**。7B 在世界知识、复杂问答和指令遵循上明显强于 3B。
2. **SG885G 的 3B 模型本身更快**：SG885G 实测约 **14.15 tok/s**，MT200 7B 约 **5 tok/s**。但今天的语音体验更差，主要不是模型速度，而是 RG660MK 前端 **麦克风丢帧、ASR 乱码、路由未命中**。
3. **内存不是当前瓶颈**：SG885G 同时加载 LLM + VLM 后仍有约 **7.3–7.8 GB MemAvailable**；RG660MK 前端可用内存约 **426–433 MB**，但日志没有 OOM，主要问题是 USB 音频采集和前端负载。
4. **看板“端侧大模型”当前实际指向 SG885G 的 `q3.gguf`**。`mt200-local` 只是历史模式名，健康文案中的 “MT200 loopback” 也是旧文字；实际链路已经是 SG885G。
5. **5B 不是当前问题的解药**：5B 估算约 9–10 tok/s，比 3B 慢约 40%，无法修复 ASR 乱码、工具失败和语音队列超时；只在知识型问答上可能略有改善。

### 4.1 MT200 7B 的实际口径

历史报告记录：

```text
模型：deepseek-7b-npu
量化：W4A16（QNN/HTP）
权重：5 个 ctx bin 分片合计 4.2 GB
上下文：1024 token
服务：npu-openai-bridge.py → genie-t2trun :8090
吞吐：约 5 tok/s
端到端：76 tokens / 15 秒
```

### 4.2 SG885G 3B 的实际口径

```text
模型：q3.gguf（Qwen2 3B）
量化：Q4_K_M
参数量：3.40B
文件：1.95 GiB
设备：HTP0
上下文：2048
线程：4
实测：约 14.15 tok/s
```

### 4.3 MT200 VLM 的历史限制

- CPU 8 线程是最佳配置；4/6 线程明显更慢。
- Vulkan/Adreno 663 GPU 路径构建成功，但加载阶段挂在 `drm_syncobj_array_wait_timeout`，未获得 GPU 加速。
- 因此 MT200 VLM 实际也是 CPU-only，与 SG885G VLM 的视觉编码器 CPU 模式类似。

### 4.4 量化口径修正

SG885G 当前的 `q3.gguf` 是 **GGUF Q4_K_M**（llama.cpp），不是 W4A16，也不是 QNN 编译模型。W4A16 只属于 MT200 的 DeepSeek 7B。

```text
SG885G：Qwen2 3B · Q4_K_M · GGUF · HTP0 · ctx 2048
MT200 ：DeepSeek 7B · W4A16 · QNN/HTP · ctx 1024
```

看板此前的 `W4A16 / ctx 1024` 文案是历史硬编码，已修正为按 `llm_gateway.describe()` 返回的 SG 实际参数显示。

## 六、为什么 MT200 的对话效果更好

### 6.1 模型规模差异是第一位

| 维度 | MT200 | SG885G |
|---|---|---|
| 模型 | DeepSeek 7B | Qwen2 3B |
| 参数量 | 约 7B | 3.40B |
| 量化 | W4A16，厂商 QNN 优化 | Q4_K_M，llama.cpp |
| 世界知识 | 更强 | 较弱 |
| 复杂指令遵循 | 更强 | 较弱 |
| 上下文 | 1024 | 2048 |

7B 对复杂问题、上下文理解、指令遵循和中文表达通常明显好于 3B；这与现场“MT200 回复更准确”的印象一致。

### 6.2 MT200 是专用 NPU 运行时

MT200 使用：

```text
npu-openai-bridge.py → genie-t2trun → QNN/HTP
```

模型和运行时是配套优化的，W4A16 权重、上下文分片、NPU 调度都经过厂商适配。

SG885G 使用：

```text
llama.cpp llama-server → HTP0（实验性 ggml-hex 后端）
```

3B 权重是通用 GGUF Q4_K_M，HTP 后端是社区/实验路径，模型质量和运行时优化都不如 MT200 的专用 7B 栈。

### 6.3 今天的“卡顿”主要是前端问题

需要区分两件事：

```text
模型推理速度：SG 3B 更快（14.15 vs 5 tok/s）
语音端到端体验：今天更差（ASR 乱码、arecord 重启、路由 miss）
```

`voice.log` 显示 ASR 拿到的是大量无意义文本，例如：

```text
“原审法的诉的我的是是是我们的诉了”
“好的好的的的的的的的的的的的的我谢谢谢”
```

这不是 3B 模型“不会答”，而是 **ASR 没有拿到用户真实说的话**。用户感知到的“卡顿/无响应”，大部分发生在模型之前。

另外，MT200 历史测试的 5 tok/s 是文本/端到端口径，今天 SG 的 14 tok/s 是模型 decode 口径；两者的测试边界不同，不能直接用“MT200 更慢”解释“MT200 体验更好”。

### 6.4 MT200 的答案更短、更直接

7B 在指令遵循上更强，通常更愿意给出短而直接的答案；3B 在同样问题上可能：

- 生成更长但重点不突出的回答；
- 对股价、算术、权限等边界问题产生不确定输出；
- 更容易被 ASR 噪声带偏。

在语音场景里，短而准确的回答会让用户觉得“顺”；长篇或答非所问会让用户反复追问，主观上更卡。

### 6.5 当前 SG 路径的额外开销

SG 本地路径比 MT200 多了一段 ADB 转发：

```text
RG → 18091 → 18090 → adb forward 28080 → SG:8080
```

MT200 历史路径是：

```text
RG → 18091 → 18090 → SSH → MT200:8090
```

两条路径都有转发，但 SG 的 ADB/USB 链路会引入额外抖动。不过本次实测 LLM 调用多在 2 秒内，转发不是首要原因；首要原因仍是 ASR 音频质量。

## 八、改进建议

### 8.1 先修前端，不要先换 5B

优先级：

```text
1. 修复麦克风采集丢帧 / arecord 重启
2. 确认 ASR 文本正确
3. 灯控、算术、股价走快速工具路径
4. 降低 RG660MK 负载或把 ASR/TTS 移到 SG
5. 再评估 5B/6B/7B
```

### 8.2 麦克风与音频

- 当前 C270 和 UGREEN CM564 都出现 `drop_ep_quirk`，说明 USB 音频链路存在共性问题。
- 建议换带供电 USB Hub、换 USB 口、关闭 autosuspend，或改用板载/模拟麦克风。
- 录音采样率先用 16 kHz 测试，减少数据量。
- 观察 `dmesg` 中 `drop_ep_quirk` 是否减少，再决定是否继续用 USB 麦克风。

### 8.3 语音路由

```text
开灯/关灯 → 直接工具，不经过 LLM
135×235 → 本地 safe_calc
股价 → 行情 API；失败明确播报“查不到”
自我介绍 → 限制 30–50 字
```

### 8.4 模型选择

| 目标 | 建议 |
|---|---|
| 语音控制、低延迟 | SG 3B + 规则快路径 |
| 知识问答、质量优先 | MT200 7B（历史最佳）或 SG 7B（需验证 HTP 映射） |
| 两者都要 | 3B 负责控制，7B 负责问答，顺序加载 |
| 5B | 只作为中间候选；不能解决 ASR/工具问题 |

### 8.5 若要在 SG 上追 MT200 的对话质量

需要单独验证：

```text
5B / 6B / 7B Q4 是否能上 HTP0
7B Q4 是否触发 fastrpc 映射上限
7B 速度是否可接受（估算 6.5–7.5 tok/s，前提是 HTP 成功）
```

在这些验证完成前，不能承诺“SG 3B 可以替代 MT200 7B 的对话质量”。

## 九、最终结论

```text
MT200 对话更好：主要是 7B 模型 + 专用 QNN 运行时
SG885G 模型更快：3B 14.15 tok/s，但质量弱于 7B
今天更卡：主要是 RG 前端麦克风丢帧、ASR 乱码、路由 miss
不是内存问题：SG 仍有 7.3–7.8 GB 可用
5B 不是解药：会更慢，且不能修复 ASR/工具链路
```

**正确的组合不是“用 5B 替换 3B”，而是：**

```text
3B / 规则快路径负责语音控制
7B 负责高质量问答
先修麦克风、ASR 和超时，再谈模型升级
```
